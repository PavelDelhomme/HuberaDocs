1. Ce que voulait dire le PDF « Hubera — 23 octobre 2026 »

Le 401 (contexte)

Des apps Cloudity/suite (Agenda, Mail, …) qui utilisent le client auth Hubera ID (/auth/refresh) affichaient une erreur quand le refresh token Redis n’était plus valide. Le correctif commun : si refresh → 401, appeler /auth/session/renew avec l’access token encore signé, sans redemander le mot de passe.

« Pas ce client » (Music, Maps, Fuel, Jobs)

Traduction claire : Music / Maps / Fuel / Jobs ne passent pas par le même petit client HTTP Hubera ID (/auth/refresh) que Agenda/Mail/Drive/Photos…

  • Chacun a son propre mécanisme de session (cookie Music, JWT Fuel, SSO AccountManager Maps, auth Jobs, etc.).
  • Donc le patch « renew après 401 refresh » du 23 oct ne les concernait pas : on ne les a pas rebuild juste pour ce bug-là.
  • Maps/Fuel ce jour-là = retouches UI (paramètres / tiroir), pas une nouvelle version auth pour le 401.

Ce n’est pas « ces apps n’ont pas d’auth ». C’est « ce correctif précis d’auth suite ne s’applique pas à leur stack ».

« La suite » (À valider ≠ Fait)

  • À valider = publié / vu en labo, toi (Paul) dois encore confirmer avant de passer en Fait. Règle Cockpit : on ne met pas Fait à ta place.
  • Photos, Notes, Cook, Pass, Tasks, ID avaient reçu l’APK du fix 401 sans que l’agent ouvre chaque écran pour prouver la disparition de la ligne 401 → donc tâche reste À valider.
